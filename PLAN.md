# Freezer Tracker — Product and Technical Plan

## 1. Goal

Build a small, phone-first freezer inventory app for two household members. It should make it quick to add a package when it goes into the freezer, find it later, and record an approximate amount remaining when some is used. Build and host the app and its data on Databricks Free Edition, with no home server.

## 2. Product principles

- **Fast at the freezer:** the common add/use flows should take only a few taps.
- **Track packages, not just product names:** two bags of the same food can have different freeze dates and quantities.
- **Approximate means approximate:** remaining grams are user-entered estimates, not computer-vision guesses or precise measurements.
- **Keep a history:** additions, uses, corrections, and discards are recorded; current stock is derived from that history.
- **Use the lakehouse for real:** persist data in Unity Catalog managed Delta tables and use Databricks transactions for atomic inventory operations.
- **Free Edition first:** keep to one app, one small schema, and light serverless SQL usage; avoid always-on or streaming infrastructure.

## 3. Proposed architecture

```text
Phone browser (HTTPS; optionally add to home screen)
        │
        ▼
Databricks App (responsive UI + API, Python and web camera-scanning component)
        │  Databricks SQL Connector; app service identity
        ▼
Serverless SQL Warehouse
        │
        ▼
Unity Catalog managed Delta tables (ACID; catalog commits enabled)
```

The app is a hosted web app, not an app-store-native phone app. It can request camera access from the phone browser over HTTPS. The initial UI should be a responsive web interface; install-to-home-screen support is a later enhancement, not a dependency.

**ACID decision:** use Delta Lake tables as the system of record, rather than adding Lakebase in the first version. Databricks supports multi-statement, multi-table transactions on Unity Catalog managed tables with catalog commits enabled. The app will perform writes through a SQL Warehouse transaction and commit an inventory change and its corresponding ledger event atomically. This directly meets the lakehouse learning goal and avoids introducing a second database. If Free Edition does not expose the required transaction features in the workspace, stop and validate that constraint before implementing the write flows; do not silently fall back to non-atomic writes.

Transactions use optimistic concurrency. If both people make conflicting changes at the same time, the app should refresh the lot balance, revalidate the requested use, and ask the user to retry if necessary. Every submission gets an operation ID so retries after a slow connection do not intentionally create duplicate events.

## 4. Feature list

### MVP — required

1. **Household access**
   - Share the app with two Databricks users in the same Databricks account.
   - Both can view and update the same inventory.
   - Attribute events to the signed-in user where Databricks app identity is available.

2. **Product identification and scanning**
   - Scan common Dutch/European retail product barcodes (EAN-13 / GTIN-13; retain the code as text so leading zeroes are not lost).
   - Also accept QR codes, including the unique QR labels generated by this app for individual freezer packages.
   - A retail barcode identifies a product, not a particular package. On a known code, show the product and let the user add a new package. On an unknown code, let the user create a product manually using the scanned code.
   - Decode a GS1 Digital Link QR to its GTIN when present. Do not assume every Dutch grocery item has a GS1 QR or that scanning a code will return product details.
   - Do not require an external product-lookup service for the MVP; Free Edition outbound network access is restricted and lookup can be added after it is tested.

3. **Add a freezer package (lot)**
   - Select/scan a product or create one.
   - Enter package quantity in grams, defaulting the freeze date to today.
   - Optionally enter freezer/drawer location, best-before date, and a short note.
   - Save the package, record its initial stock event, and show a printable unique QR label with a readable product name, quantity, and date.

4. **Inventory overview**
   - Show products and their individual packages/lots, estimated grams remaining, date added, and location.
   - Search by product name or code; filter by location and show empty/low-stock and oldest items.
   - For products with several lots, show each lot separately and suggest using the oldest first. Never silently combine or consume lots.

5. **Record use and corrections**
   - Scan a package QR or select a package from the inventory.
   - Record grams used, enter the estimated grams remaining directly, or choose simple estimates such as “use half.”
   - Label the event as a user estimate; allow a weighed amount when the user has one.
   - Prevent a normal use action from taking a lot below zero. Provide a correction/adjustment action for mistakes and an explicit discard/empty action.
   - Show the new approximate balance and allow a recent event to be reversed by creating a compensating event (do not delete the audit history).

6. **History and data export**
   - Show a package’s add/use/adjust/discard timeline, including timestamp, amount, estimate/measurement method, and actor when available.
   - Provide a simple CSV export for backup and inspection.

### Later, only if the MVP is useful

- Optional product-name/brand lookup from a GTIN, subject to Free Edition network availability and the service’s terms.
- Low-stock shopping list, configurable reminders, and household consumption/waste dashboards.
- A true installable PWA experience and a printable sheet of multiple labels.
- More units (pieces, millilitres) alongside grams; recipe suggestions; photo-assisted estimates. Photo/AI estimates are explicitly out of scope for the first version.

## 5. Data model

Use a dedicated Unity Catalog schema (catalog and schema names are configured for the workspace). Tables are Unity Catalog **managed Delta** tables with catalog commits enabled.

- **`products`** — `product_id`, display name, optional brand, optional GTIN/EAN as text, preferred unit, optional usual package size, created/updated timestamps.
- **`lots`** — `lot_id` (also the unique QR payload), `product_id`, frozen/added date, optional best-before date and location, notes, created timestamp.
- **`inventory_events`** — `event_id`, idempotency/operation ID, `lot_id`, event type (`STOCK_IN`, `USE`, `ADJUST`, `DISCARD`, `REVERSAL`), signed `quantity_delta_g`, timestamp, actor, measurement method (`ESTIMATE`, `WEIGHED`, `CORRECTION`), optional note, and optional reference to the reversed event.
- **`v_current_lot_stock`** — a view that sums each lot’s event deltas and joins product/lot details. Negative balances are surfaced as data-quality errors, not hidden.

Stock-in is a positive event; use/discard are negative events; adjustments are signed. The UI displays “about N g” for estimates. Retaining events makes corrections auditable and supports later analytics. Databricks primary/foreign-key declarations are not a substitute for application validation; validate references and business rules in the transaction.

## 6. Atomic write behavior

- **Add package:** in one transaction, create a new product if needed, create the lot, and insert its positive `STOCK_IN` event.
- **Use/adjust/discard:** in one transaction, read the current lot balance, validate the request, and insert the corresponding event. If there is a concurrent-write conflict, roll back, refresh, and revalidate.
- Use short transactions, explicit commit/rollback, parameterized SQL, and an operation ID for retries. Never let browser JavaScript connect directly to Databricks or hold credentials.
- Bootstrap tables and grants separately. The app identity should have only the warehouse/schema permissions needed by the app.

## 7. Free Edition fit and constraints

- The design needs **one Databricks App** and **one SQL Warehouse**; it does not need Lakebase, a continuously running job, or a streaming pipeline.
- Free Edition currently permits up to three Apps and provides serverless compute, but an App is automatically stopped after 24 hours and must be restarted. Free Edition quotas are subject to fair use and can make compute unavailable temporarily; it has no SLA.
- Persisted Delta data remains in the workspace when the App stops. The app’s availability is the main household-use caveat, not the storage size or two-person write volume.
- Verify in the actual workspace that the app can bind to a SQL Warehouse, that interactive transactions and catalog commits are available, and that the second user can open the shared app. These are early feasibility checks.
- Keep the initial workload to interactive reads/writes and occasional manual analytics. Do not add a polling loop or scheduled job just to keep the app alive.

## 8. Build and validation milestones

1. **Free Edition feasibility spike:** create/share a tiny App, confirm the second user can access it, connect to a serverless SQL Warehouse, and run/rollback a two-table Delta transaction with catalog commits. Confirm the 24-hour stop/restart experience.
2. **Schema and seed data:** create managed Delta tables, event-derived current-stock view, and a few sample products/lots. Validate the view with SQL.
3. **Phone-first app shell:** responsive inventory list, product form, add-lot flow, and app identity/access handling.
4. **Ledger and transactions:** implement add/use/adjust/discard, idempotency, nonnegative-balance checks, conflict handling, and audit history.
5. **Scanning and labels:** add browser camera scanning for QR and EAN/GTIN formats, unknown-code flow, and package QR label printing. Test on the actual phones and freezer lighting/labels.
6. **Hardening:** test concurrent use by both people, transaction rollback on errors, repeat submissions, camera denial/manual entry, stale app restart, CSV export, and data recovery using Delta history/backup procedures.
7. **Optional analytics:** build a small Databricks SQL dashboard or notebook from the Delta event data; only add automation if Free Edition usage allows it.

## 9. MVP acceptance criteria

- Either household member can add a package with product, grams, and date; the lot gets a unique QR label.
- Scanning the package QR opens the correct lot; scanning a known retail EAN/GTIN selects the product for a new lot; unknown codes can be saved manually.
- A user can record grams used or set an approximate remaining amount, and the inventory updates from the ledger.
- An add or use operation either commits all of its related changes or commits none of them.
- Repeated requests do not intentionally double-count; invalid or conflicting updates are explained and recoverable.
- Both users can see each other’s committed updates, and the app records the actor when identity is available.
- All inventory persists in Unity Catalog managed Delta tables after an App stop/restart; no home server is required.
- The Free Edition 24-hour stop and restart behavior is understood and acceptable to both users before treating this as the household’s sole inventory record.
